# 한국어 자연스러움·마케팅 품질 워크플로

> 2026-10-15 — 개선 2단계: 통합 검토와 필요한 부분만 윤문

이 문서는 `im-not-ai`(기존 humanize-korean quick-rules 포함)와 마케팅 스킬을 콘텐츠에 적용하는 순서를 정한다. 스킬은 사실을 만들거나 에토스 지침을 덮어쓰는 권한이 없다. Codex에서 전체 파이프라인을 실행하는 진입점은 `.agents/skills/ethos-humanize/SKILL.md`다.

## 적용 원칙

블로그는 `docs/blog-authoring-spec.md`, 카드 초안은 `docs/card-authoring-spec.md`의 빠른 경로와 역할 분담을 우선한다. 이 문서의 항목을 채널 명세 뒤에 추가 패스로 붙이지 않는다. 블로그의 근거 확인 A·B·C와 도구 사용 강도는 별개이며, 도구를 적게 쓴다고 법률 확인을 생략하지 않는다.

새 글·후속편·새 시리즈·수정본 및 블로그·웹사이트·카드·카카오톡·LinkedIn·Instagram·Threads·X·숏폼의 파생물에 **독자의 질문을 풀어 가는 칼럼형 설명, 법률 근거·조건·예외, 실제 맡길 작업과 다음 행동**을 함께 적용한다. 카드와 숏폼은 세트·대본 전체에서 연결하고 문장마다 세 요소를 강제하지 않는다. Traffic·Authority·Revenue의 주 역할이나 언어 차이를 이유로 어느 요소도 생략하지 않는다.

자연스러움 검수는 필요하지만 **모든 원고를 외부 AI로 다시 쓰거나 새 검수 패스를 여러 개 추가하는 것이 의무는 아니다.** 기존 채널 명세로 읽어보고 수정할 곳이 없으면 그대로 둔다. 실제 윤문이 필요하면 고정 버전의 `vendor/im-not-ai/quick-rules.md`로 직접 부분 편집하거나 `.agents/skills/ethos-humanize/SKILL.md`에 따라 공식 im-not-ai의 진단→겨냥 윤문→게이트(필요한 경우 finalize)를 실행한다. 두 방법을 같은 문장에 반복 적용하지 않는다. 실제 사용한 방법을 구분하고 원문 대비 법률 의미를 직접 확인한다.

**GitHub PR 자동 스캔과 전체 윤문은 다른 단계다.** `Prose hints`는 고정된 im-not-ai v2.3.2의 정량 shim과 에토스 지시형 어투 힌트를 비차단 참고로 출력한다. PR 검사만으로 전체 85개 패턴을 LLM으로 고치거나 법률 검증을 완료한 것이 아니다. 자격·처분·영업등록의 정확한 금지와 주의는 유지하고, 집필자 지시처럼 새어 나온 '적용해서는/옮겨서는/설명해서는 안 됩니다'는 실제 적용 기준과 독자가 할 일로 설명한다. 에토스의 짧고 쉬운 문장 우선 원칙상 upstream E-1 장문 생성 권고는 계속 제외한다. 상위 소스는 커밋으로 고정하고 무단 자동 업데이트·원고 덮어쓰기·추가 유료 API 호출을 하지 않는다.

기본은 한 작성자가 초안 뒤에 통합 검토하고 필요한 부분만 고치는 방식이다. 근거 충돌·누락, 복잡한 조건 분기, 기한 계산이나 업무범위 의문이 남을 때만 해당 쟁점을 집중 검토한다. 자세한 선택 기준은 `docs/tooling-policy.md`이며, 여기의 요약으로 해결되면 추가로 읽지 않는다.

공통 작성 원칙은 `docs/brand-philosophy.md`, 근거 선택·검증은 `docs/evidence-gate.md`가 정본이다. 이 문서는 실행·윤문 순서를 맡는다. 질문과 실제 판단 이유를 쉬운 말로 잇고 예시 다음 문단도 추상 명사로 되돌리지 않는다. 절차를 모든 글의 틀로 강제하지 않고, 이름·대화는 선택하며 실제 경험을 지어내지 않는다.

공개 본문·캡션에는 독립적인 확인 기준일 라벨을 넣지 않는다. 확인일·판본은 내부 검증 기록에 보존하고 법령 시행일·판결일·통계기간은 유지한다. 영문·아랍어에도 같은 원칙을 적용한다.

## 실행 순서

아래는 확인 순서이지 별도 모델 호출이나 에이전트 수가 아니다. 기존 여덟 항목의 사실·법률·윤리·문체·의미 검증을 네 묶음으로 수행한다.

1. **필요한 근거 선택·확인**: 초안 전에 중심 질문과 직접 관련된 실제 사건·회신·통계·보도·행정자료를 기존 research에서 우선 검토하고 공백만 추가 조사한다. 적합한 자료는 쟁점과 설명을 이끌게 쓰며 종류별 의무 수는 없다. 없으면 검증된 법령·공식 안내로 설명한다. 채택·제외 이유는 기존 기록에 필요한 만큼 남긴다. 파생은 승인 원문의 근거·판단 이유를 재사용한다.
2. **자연 초안**: 독자가 품은 의문과 오해를 드러내고, 왜 판단이 달라지는지 이해하며 자신의 상황에 적용하는 흐름을 초안에서 만든다. 독자의 상황과 질문에 설명하듯 끝까지 쓴다. 문장마다 규칙을 적용하거나 문형·예시 개수를 맞추지 않는다. 기존 제목의 질문과 도입, 유용한 예시와 필요한 법률적 깊이는 살린다. 수수료·기한·필수서류는 찾기 쉬운 목록과 설명으로 남긴다.
3. **통합 검토**: 기존 최종 3질문 안에서 실제 근거가 답과 설명에 쓰였는지, 예시 뒤 설명도 쉬운지, 독자가 직접 할 일과 맡길 업무를 구분할 수 있는지 확인한다. 별도 점수표·재작성 패스를 더하지 않는다. 먼저 원문과 초안의 사실·법률·인용을 대조한다. 이어 질문과 답이 연결되는지, 근거에서 결론으로 가는 사이 조건·예외가 빠지지 않았는지 본다. 실제 자료로 무엇을 하고 어떤 문서나 다음 절차를 준비하는지, 직접 확인 범위와 무료·유료 경계가 분명한지도 함께 살핀다. 창작한 경험·성과·공포와 채널 부적합 표현은 배제한다. 법률·논리·마케팅마다 원고 전체를 다시 쓰지 않는다.
4. **부분 편집과 의미 재확인**: 발견된 약점만 고친다. 어색한 문장은 앞뒤 문맥과 함께 윤문하고, 바뀐 문장 및 영향을 받는 제목·요약·결론에서 주체·조건·예외·숫자·조문·인용·업무범위가 유지됐는지 확인한다. 의미가 달라진 수정은 되돌리거나 근거에 맞게 다시 고친다. 문체 문제가 없는 부분은 변경하지 않는다.

한 차례 통합 검토는 기본값이지 오류를 남기는 상한이 아니다. 정확성 문제가 남으면 해당 쟁점의 추가 근거 확인을 이어간다. 독립적인 논리 도구나 다중 에이전트가 필요한지는 구체적인 미해결 문제로 판단한다. 도구의 답만으로 법률 확인을 완료했다고 기록하지 않는다.

## 자연스러운 문제 해결형 설명 (2026-10-15 보강, Soft Guide)

`docs/brand-philosophy.md`와 블로그 명세의 독자 이해·수행 업무 원칙을 적용한다. 새 검수 패스를 추가하지 않고 아래 관점으로 읽히지 않는 곳만 고친다.

- **질문과 답을 잇는다.** 독자가 차량 사용이나 계약 진행을 물었다면 그 질문의 답을 먼저 준다. 기한 확인·상담 권유·"검토 필요"로 대답을 대신하지 않는다. 기존 제목의 의미와 도입의 역할을 보존한다.
- **짧은 문장부터 쓰고, 생각은 자연스럽게 연결한다.** 한 문장에 판단·조건·예외·업무를 한꺼번에 넣지 않는다. 먼저 누가 무엇을 해야 하는지 쉬운 말로 설명하고, 이유·법정 용어·추가 조건은 필요한 다음 문장으로 나눈다. 문단은 한 가지 생각을 이해할 만큼 이어 쓰되 짧게 구분하고, 문장마다 줄을 바꾸는 메모체나 똑같은 짧은 문장만 반복하는 리듬은 피한다. 기계적인 글자 수·문장 수 제한을 만들지 않고 법률상 주체·의무·재량·예외를 보존한다. 어린 학생에게 처음 가르치듯 이해하기 쉽되 독자를 어린아이로 대하거나 전문성을 낮추지 않는다.
- **실제로 쓰는 한국어인지 확인한다.** 소리 내어 읽어도 매끄럽지 않은 문장은 주어·서술어와 문장 끝의 동사부터 고친다. '여기에 연결됩니다', '이러한 차이가 나타납니다', '이와 관련되어 있습니다' 같은 말이 실제 관계나 차이를 설명하지 않고 문장을 끝내기 위해 붙은 것이라면 없앤다. '정하는 일이 연결됩니다'보다 누가 무엇을 확인하고 정하는지 바로 쓴다. 한자어를 쉬운 말로 바꾸는 것과 한국어 어법이 자연스러운지는 별도로 본다. 자동 치환·전면 재작성이나 새로운 검수 패스를 추가하지 않고 기존 윤문 단계에서 어색한 부분만 고친다. 의무를 뜻하는 '해야 한다'를 단순한 '관련이 있다'로 약화하는 등 법률 의미를 바꾸지 않는다.
- **집필자용 금지 지시를 독자용 설명으로 바꾼다.** '적용해서는 안 됩니다', '옮겨서는 안 됩니다', '설명해서는 안 됩니다'와 같은 어투가 작성자 자신의 법률 해석을 경계하는 말인지, 법령상 실제 금지나 독자가 지켜야 할 주의인지 먼저 구분한다. 전자라면 독자가 따를 구비서류 기준·적용 조건·법적 효과를 평서문으로 직접 설명한다(예: '제조업 등록서류를 책임판매업 서류로 옮겨서는 안 됩니다' → '책임판매업 신규등록은 책임판매업의 구비서류 목록을 기준으로 준비합니다'). 후자라면 실제 금지의 강도와 주체를 유지한다. 기계적인 긍정문 치환, 모든 부정문 제거, 새 검수 패스는 하지 않는다. 이 기준은 `humanize-korean` 수동 윤문과 AI 제안 양쪽에 적용하지만 실제로 스킬·검사를 실행하지 않았다면 실행했다고 기록하지 않는다.
- **예시 뒤에도 설명을 이어간다.** 원문에 있는 상황·날짜·서류를 이용해 왜 차이가 생기는지 설명한다. 쉬운 예시 뒤에 추상적인 법률 명사만 나열하지 않는다. 업종 독자에게 익숙한 장면과 예시 대화를 활용하되 허구를 실제 경험으로 주장하지 않는다. 이름만 바꾼 동일 설명이나 감정 과장은 피한다.
- **마케팅은 실제 업무를 보이는 편집이다.** '검토·지원·대응' 대신 어떤 자료의 무엇을 맞춰 어떤 문서나 안내를 준비하는지 보여준다. 서비스 범위가 확인된 작업만 쓰며 범위가 없으면 원문 보강 사항으로 남긴다. 작업의 완료와 허가·처분 변경 같은 외부의 결정을 구분한다. 모든 절에 사무소 소개나 상담 권유를 삽입하지 않는다.
- **자연스러움과 정확성을 함께 지킨다.** 법률상 용어·숫자·조건·예외는 설명을 붙여 보존한다. 쉬운 글을 분량 축소와 동일시하지 않으며, 새 사례 수·산출물 수·점수 기준을 만들지 않는다. 편집 완료를 실제 문의·수임 증가로 평가하지 않는다.

원문과 실제 제공 업무에 근거가 있는 경우의 표현 예: "문서 정합성을 검토합니다" → "계약서와 신청서의 날짜가 같은지 맞춰 보고, 서로 다른 부분을 정리합니다." 문체 예시이지 모든 업무에서 제공하는 서비스나 무료 범위에 대한 약속은 아니다.

## 독자 이해 편집과 윤문의 경계

- **신규 원고 초안**에서는 독자 상황·첫 전문용어 풀이·조건이 다른 예시를 필요한 만큼 구성할 수 있다. "신청서와 증명서의 이름이 다르다면?"처럼 조건문으로 예시임을 드러내고 공식 근거와 대조해 법률상 의미를 검증한다. 발행 본문·카드·캡션·자막에 "설명을 위한 가상 상황입니다", "가상의 사례입니다", "실제 상담 사례가 아닙니다" 같은 독립 안내문을 넣지 않는다. 안내문만 지우고 허구를 실제 사건처럼 바꾸거나 예시 인물을 실제 고객으로 소개하거나 실제 상담 대화·후기·수임 성과를 지어내지 않는다. 다양한 예시 이름과 짧은 대화 자체는 허용한다. 생활 장면은 설명의 출발점이며 새 법률 결론의 근거가 아니다.
- **독자 이해 편집**은 '이 문단을 읽고 자신의 통지서나 계약서에서 무엇을 확인할지 알 수 있는가'를 보는 작업이다. 설명이 막힌 곳만 예시·대조·풀이를 보강하며, 추가한 내용은 다시 근거와 대조한다. 블로그에서는 별도 전면 재작성 패스로 만들지 않고 자연 초안과 약한 부분의 보완에 포함한다.
- **최종 윤문**은 표현·리듬을 고치는 작업이다. 승인된 Source Lock에 없던 사실이나 가상 사례를 윤문 도구가 새로 덧붙여서는 안 된다. 새 인물·대화·장면이 꼭 필요하면 원문 초안 보강으로 되돌아가 법률 의미 검증·승인을 거쳐 Source Lock에 포함한 뒤 파생한다.
- **파생 콘텐츠**는 승인된 블로그의 사실·조건·사례를 Source Lock으로 삼는다. SNS·카드·웹사이트·번역에 새 인물·대화·장면을 더하려면 원문 보강·검증·승인을 먼저 거친다. 원문에 없는 사실관계나 결과를 임의로 추가하지 않는다.
- 사례의 유무와 개수, 질문형 제목 비율, 쉬운 말의 양을 점수로 강제하지 않는다. 핵심은 독자가 답·조건·확인 행동을 이해하는지다.

## humanize-korean 보호 범위

다음은 바꾸지 않는다.

- 법령명·조문·판례·재결례·기관명
- 숫자·날짜·금액·기한·비율
- 직접 인용·출처·고유명사
- 공식 용어와 Evidence Label
- 사실관계와 법률상 조건·예외
- 무료 검토, 유료 상담, 수임의 범위

윤문은 번역투, 기계적 병렬, 관용구, 접속사 반복, 문장 리듬을 다듬는 데 한정한다. 새로운 경험담·비유·성과·긴급성·감정을 추가하지 않는다. 자동 윤문 제안의 기존 수락 기준인 변경률 30% 이하와 보호 범위 검사는 유지한다. 기준을 넘거나 의미가 달라진 제안은 채택하지 않는다. 그 제안이 거부됐다는 이유로 원고 전체를 폐기하거나 비율을 낮추려고 자동 윤문을 반복 호출하지 않는다. 필요한 부분을 직접 고치고 의미를 확인한다. 이 문서는 자동 검사 코드의 임계값을 변경하지 않는다.

## 카드뉴스 적용 시점

- 카드 카피: ChatGPT는 자연 초안과 필드 압축까지만 맡는다. Codex는 초안을 검수하고 국문 card-data 승인 요청 전에 필요한 윤문과 의미 재검증을 마친다. 승인 뒤에는 Source Lock을 우선하며 다시 윤문하지 않는다.
- 카드 문장은 일반 본문처럼 길게 풀지 않는다. 한 장 한 메시지, 말하듯 읽히는 제목, 문장 길이 변화, 반복 종결어미 제거를 우선한다.
- `확인해야 합니다`, `중요합니다`, `검토가 필요합니다` 같은 동일 결말을 연속 카드에 복제하지 않는다. 질문·직접 답변·대조·짧은 결론을 메시지에 맞게 섞는다.
- 국문 card-data에는 각 단계의 실제 완료 상태를 `pass`·`pending`으로 기록한다. 초안의 `pending`은 정상이며 승인 전 비교용 미리보기와 발행을 구분한다. 하지 않은 단계를 완료로 바꾸지 않고, 최종 승인·발행 요건은 카드 작성 명세와 Codex 제작 절차를 따른다.
- 캡션·alt text: 사실 검토 후 발행 직전에 필요한 부분을 윤문할 수 있다.
- 영문·아랍어: `humanize-korean` 대상이 아니다. 각 언어의 별도 현지화·검수 절차를 사용한다. 표현과 업무 문맥은 현지화하되 국문 근거와 주체·대상·의무/재량·조건·예외·숫자·출처 및 무료·유료 서비스 범위를 대조한다. '또는', '이하', '수 있다'의 의미와 질문의 방향을 보존하고, 번역으로 새 사례나 서비스 약속을 만들지 않는다. 공식 명칭이나 의미를 확인하지 못한 부분은 검수 완료로 기록하지 않는다.

## 실패하지 않는 운영과 종료

스킬을 실행하지 않았으면 실행한 것처럼 말하지 않는다. 채널 명세로 직접 검수했는지, 규칙집을 참고해 부분 윤문했는지, 외부 제안을 받았는지를 기존 작업 메모에 짧게 구분한다. 새 보고서나 점수표는 요구하지 않는다. 검수 후 수정할 곳이 없었다는 기록도 가능하다.

카드 JSON의 `languagePass`에는 담당 검수를 실제로 마쳤을 때 `pass`, 하지 않았으면 `pending`만 쓴다. 사용 방법의 이름을 단계 값으로 넣지 않는다. 초안 작성은 계속할 수 있지만 필요한 검수가 끝나지 않은 결과를 발행용 완성본이라고 보고하지 않는다.

정확성·업무범위·인용·필수 형식의 문제가 해결되고 독자의 질문에 답하며 실제 작업이 이해되면 편집을 마친다. 실제 결함이 없으면 문체 점수나 형식 권고 때문에 다시 쓰지 않는다. 기준을 충족한 블로그를 11,000자에 맞추려 분량을 덧붙이지 않는다. 미확인 법률 내용이나 필수 검사 실패를 속도 때문에 넘기지 않는다.

**검수 완료 원고의 재평가**: 사용자 편집본과 이미 완료로 판단한 글은 재평가할 때 새로 확인된 법률·사실 오류, 필수 형식 위반, 선택적 표현 개선을 구분한다. 앞의 두 문제는 해당 구절과 영향을 받는 범위를 바로잡되, 선택적 개선 아이디어만으로 전면 재작성을 요구하지 않는다. 완료 판단을 바꾸려면 기존 평가 뒤 새로 확인한 구체적 문제와 근거를 설명한다. 개선할 여지를 계속 찾아내는 일을 종료 요건으로 삼지 않는다.

아래 기술 참고는 기존 도구를 실제로 사용할 때만 읽는다. 설치·API 호출·기존 자동화의 실행 조건은 별도 운영 범위이며, 이 문서 정리를 이유로 활성화하지 않는다.

## 코드로 확인하는 항목 (`scripts/copy_lint.py`)

윤문 단계 기록(`languagePass`)은 자기 선언이다. 아래 항목은 실제 카피를 읽고 확인하므로 최종 승인 요청 전 담당자가 실행하고 경고를 처리하거나 의도적으로 남긴 이유를 `reviewNote`에 적는다. 임계값은 `copy-rules.json`에서 조정한다. ChatGPT 카드 초안 단계에 새 실행 의무를 추가하지 않는다.

- 질문형 헤드라인이 20%를 넘는지, 한 형태(질문·대비·숫자·단정)가 절반을 넘는지
- 제목·결론이 부정문(`~아닙니다`, `~않습니다`)으로 끝나는 카드가 30%를 넘는지
- 카드 한 장의 조문 번호가 1개를 넘는지. 근거 조문은 캡션 근거 줄로 옮긴다
- `content/<ID>/terms.json`에 등록한 전문용어가 첫 등장에서 풀이(`—`·`:`·괄호·`이란`) 없이 쓰였는지
- 표지가 끝까지 보면 얻는 답(`promise`)을 약속하는지. 숫자 없는 약속도 허용하며 유용성은 편집자가 판단한다
- 국·영문 질문의 방향(`없어도 될까요?` ↔ `need`)이 뒤집히지 않았는지
- 캡션에 저장 이유가 있는지(주 목표가 저장일 때), `출처 입력` 같은 자리표시자가 남지 않았는지
- `--compare`: 윤문 전후의 조문·판례번호·금액·날짜가 그대로인지. 카드에서 빠진 토큰이 캡션에 남아 있으면 info로 표시한다

린터가 통과해도 자연스럽다는 뜻은 아니다. 소리 내어 읽었을 때 어색한 문장은 사람이 고친다.

## 실제 활용: 초안 → PR → 필요한 문장만 고치기

- **채팅에서 원고를 작성하는 단계**: 작성자가 먼저 자연스러운 한국어와 법률 의미를 함께 점검한다. 채팅 출력만으로는 GitHub Actions가 실행되지 않으므로, GitHub 검사 완료라고 말하지 않는다.
- **원고를 GitHub content 폴더에 저장하고 PR을 여는 단계**: 기존 `Prose hints` 워크플로가 변경된 `blog.md`, `website.ko.md`, `card-data.ko.json`, `distribution.md`, `caption.ko.md`를 대상으로 작동한다. 카드 JSON에서는 독자가 보는 국문 문구만, 배포안에서는 Korean 절만 뽑는다. 사용자 원고·게시물을 자동 덮어쓰지 않는다.
- **검사 결과를 읽는 단계**: MuncheKit·ko-mt-lint의 오류 후보와 에토스가 실제로 겪은 어색한 연결말 후보를 PR 댓글에 받는다. 법률용어·의무·재량·숫자·예외를 보존하면서 **실제로 어색한 문장만** 수정한다. 도구가 설치되지 않았으면 ‘도구 없음’으로 표시하고 통과했다고 주장하지 않는다.
- **선택적 추가 윤문**: 외부 유료 API가 설정된 카드 작업만 기존 `AI polish suggestions`를 사용할 수 있다. API 사용, 시크릿 등록, 자동 수정은 이번 경로의 기본값이 아니며 사용자에게 새로운 API 비용을 발생시키지 않는다.
- **오픈소스 규칙의 충돌 처리**: `humanize-korean`의 E-1(100자 이상 문장을 만들어 리듬을 맞추라는 권고)은 에토스 법률 칼럼에는 적용하지 않는다. 이미 쉬운 문장은 유지하고, 긴 문장을 더 만들지 않는다. 이 예외는 `scripts/ai_polish.py`의 에토스 우선 규칙에도 반영한다.
- **완료**: 실제 오류를 고치고 3질문을 충족하면 재작성 없이 종료한다. 예시 표현이 자연스럽다고 자동 판정할 수는 없으므로 최종 국문 문장과 법률 의미는 사람이 확인한다.

## 자동 윤문 제안과 형태소 검사

- `scripts/copy_lint.py`는 `kiwipiepy`(Apache-2.0)가 설치돼 있으면 결론 문장의 어미를 형태소로 분석해, 같은 어미가 4장 이상 이어지면 알려 준다(`ending-run`). 없으면 이 검사만 건너뛴다.
- 같은 `kiwipiepy`로 띄어쓰기 교정 후보도 알려 준다(`spacing`). 표준 맞춤법과 맞는 두 경우만 남긴다: 의존 명사 띄우기('받을수' → '받을 수', '하는것' → '하는 것'), 명사 뒤 '하다' 붙이기('제출 할' → '제출할'). 형태소 분석기가 제안하는 합성어 분리('영업정지' → '영업 정지')나 비표준 붙임('해야 할' → '해야할')은 버린다. 권고(info)이며 LLM이 아니다.
- 영문은 `vale`(MIT)이 설치돼 있으면 저장소 `.vale-en.ini`의 Microsoft·write-good·proselint 규칙으로 장황한 표현·긴 문장을 알려 준다(`en-vale`). 법률 영어에 필요한 수동태와 한정어(generally, several, may) 지적은 꺼 두었다. 한정어를 지우라는 제안이 나와도 따르지 않는다. 설치: `pip install vale` 후 저장소 루트에서 `vale --config=.vale-en.ini sync` 한 번. `Render cards` 워크플로는 자동으로 설치한다. `scripts/validate_website_md.py`도 같은 힌트를 INFO로 보여 준다.
- 원고 PR에는 `Prose hints` 워크플로가 오픈소스 린터 두 개의 힌트를 댓글로 단다(`scripts/prose_hints.py`). MuncheKit(MIT)은 번역투(`~에 대한`), 생성형 상투 대구("단순한 A를 넘어 B"), 명사화("검토를 진행했다"), 겹말("사전에 미리"), 근거 없는 강조("매우 중요한"), 문두 접속어 남용을 본다. "~할 수 있다"를 빼라는 규칙(KO-POSS-001)은 법률 한정어를 지우므로 `.munche.json`에서 꺼 두었다. ko-mt-lint(MIT)는 LLM 초안의 활용 오류("했는다")·조사 중복을 본다. 둘 다 권고다.
- `humanize-korean` 단계는 `scripts/ai_polish.py`로 실행할 수 있다. 규칙집은 `vendor/im-not-ai/quick-rules.md`(MIT)이고 자동 제안에는 유료 Claude API를 쓴다. ETHOS 기준은 자동 윤문 제안의 변경률 **30% 이하**다(상위 기준이 vendor의 50%보다 보수적). 사실 토큰·숫자·인용·링크·한정어 수 보존과 금지 문구 미추가를 검사한다. 판례 인용(`quote`) 카드 전체와 키·라벨은 수정 대상으로 보내지 않는다.
- PR에서 `card-data.ko.json`이 바뀌면 `AI polish suggestions` 워크플로가 제안을 PR 댓글로 남긴다(시크릿 `ANTHROPIC_API_KEY` 필요, 없으면 건너뜀). 파일은 고치지 않는다. 채택은 사람이 하고, 채택 후 의미를 다시 확인한다. 방법은 별도 메모로 남기며 카드 JSON의 `languagePass`는 실제 검수를 마쳤을 때만 `pass`로 기록한다.
- 영문은 이 자동 윤문 대상이 아니다.
- API 없이도 필요한 윤문은 가능하다. 해당 단계 담당자가 채널 명세와 실제로 읽은 `vendor/im-not-ai/quick-rules.md`로 직접 다듬고 의미를 대조한다. API 미사용을 이유로 같은 원고의 추가 패스를 요구하지 않는다. 기존 `Render cards` 워크플로의 사실 토큰·한정어 비교는 유지한다.

## 문맥을 포함한 카드·블로그·SNS 검수

- 카드 제안에는 핵심 메시지, 앞뒤 카드 메시지, 현재 카드, Source Trace 및 원문에서 실제로 찾은 근거 구간을 함께 준다. 근거를 찾지 못하면 빈 값으로 두며 만들어 넣지 않는다.
- 블로그·SNS는 문단과 앞뒤 문단을 함께 읽는다. 카드가 없는 작업 폴더도 `python scripts/copy_lint.py content/<ID> --blog`로 검사할 수 있다. 국문 캡션에도 반복·띄어쓰기·결론 회피 힌트를 적용한다.
- Kiwi의 `split_into_sents`로 한국어 문장을 나눈다. 사용 불가 시 정규식으로 대체한다. 질문·부정·어미 비율은 `info`이며 `--strict`에서도 실패시키지 않는다. Vale의 `ETHOS.EditorialClarity`는 실제 중복·결론 회피 표현을 비차단으로 표시한다.
- 주체·행위·대상·조건·예외·의무/재량·CTA 범위는 의미 재검증 때 따로 대조한다. 같은 토큰 개수는 의미 보존의 충분조건이 아니다.
- `--apply`로 카드 제안을 반영하면 기존 `approvedBy`를 제거하고 사실·언어·의미 검수를 `pending`으로 되돌린다. 제안 채택만으로 검수 완료를 기록하지 않는다.
- 블로그·SNS는 제안만 출력하며 자동 덮어쓰기를 지원하지 않는다. 헤딩·목록·표·코드 블록은 수정 대상에서 제외한다. SNS 파일에는 게시할 국문 본문만 넣는다(국·영문과 내부 메타데이터가 섞인 distribution.md 전체를 보내지 않는다).

```bash
# API 없이 요청 문맥을 출력해 수동 윤문에 사용
python scripts/ai_polish.py content/<ID> --print-request
python scripts/ai_polish.py --text content/<ID>/blog.md --print-request
python scripts/ai_polish.py --text content/<ID>/caption.ko.md --channel sns --print-request
# API가 설정돼 있으면 문단 단위 수정 후보와 이유를 보고서로 출력
python scripts/ai_polish.py --text content/<ID>/blog.md --report content/<ID>/polish.md
```

확인된 결론은 먼저 분명히 쓴다. 근거 없는 양시론을 없애되, 원문에 필요한 조건과 재량 표현을 삭제해 단정하지 않는다(`guidelines/core/definitive-style.md`).


## 문맥·예시 연결과 기록 호환

`scripts/writing_context.py --purpose opening|flow|polish|card`는 기존 문체 예시집의 관련 절만 읽기 전용으로 출력한다. 예시는 표현·문단 연결·중복 제거의 이유를 참고하는 자료이며 현재 원고의 사실 근거가 아니다. `ai_polish.py --print-request`와 실제 윤문 요청은 동일한 선택 예시를 포함한다. 유료 API 호출 없이도 이 입력을 보고 수동으로 검토할 수 있다.

문장 교정 전에 도입의 답과 다음 문단의 새 정보가 이어지는지 확인한다. 어미·질문·부정문 비율을 맞추기 위해 자연스러운 문장을 고치지 않는다. 원고 구조 변경은 별도 제안이며 자동 적용하지 않는다.

새 기록은 `languagePass: pass/pending`과 실제 방법 `languageMethod`를 분리한다. 완료일 때만 방법을 기록하고, 윤문 제안을 적용하면 방법 기록을 제거하고 사실·언어·의미 검증을 pending으로 되돌린다. 과거 승인 파일의 방법명 형태 languagePass는 그대로 읽으며 일괄 마이그레이션하지 않는다.

## 승인 원고를 보존하는 별도 초안 비교

사용자가 개선안 비교를 요청하면 승인 원고와 분리된 초안 폴더를 만든다. 편집 전에 아래 첫 명령으로 원본 파일의 SHA-256을 기록하고, 편집·렌더 후 두 번째 명령으로 다시 대조한다. 기존 스냅샷은 덮어쓰지 않는다.

```bash
python scripts/editorial_compare.py --baseline content/<승인ID> --draft content/<초안ID> --initialize
python scripts/editorial_compare.py --baseline content/<승인ID> --draft content/<초안ID>
```

초안의 `condition-map.json`에는 원문 조건별 정확한 발췌와 각 언어 카드의 페이지·발췌를 연결한다. 긴 법률 설명을 나눌 때 `또는`으로 갈리는 대안과 함께 충족해야 하는 조건(AND/OR), 예외의 적용 범위, 의무·재량을 카드 사이에서도 읽을 수 있게 남긴다. 필요한 조건을 캡션에만 숨기지 않는다. 발췌가 있다는 자동 검사는 추적 여부만 확인하므로, 담당자는 나뉜 카드를 순서대로 읽고 법률 의미를 따로 검토한다.

사실·법률 검토 뒤 필요한 문장만 humanize-korean으로 다듬고 바뀐 구절의 의미를 다시 확인한다. 승인본과 초안은 같은 화면 크기·폰트·배율로 실제 렌더해 나란히 비교한다. 글자 크기·카드별 문량·넘침은 측정값으로, 자연스러움·읽기 흐름은 구체적 전후 구절과 이미지로 설명한다. 문량 감소나 자동 QA 통과를 품질 개선율로 바꾸지 않는다.

비교 미리보기는 사용자 승인이나 발행을 뜻하지 않는다. `approvedBy`를 복사하거나 검수하지 않은 단계를 `pass`로 올리지 않는다. 발견된 문제와 채택한 편집 이유를 기존 검수 메모에 남겨 다음 초안에서 참고하되, 새 점수표·강제 카드 수·자동 원고 재작성 규칙을 만들지 않는다.
