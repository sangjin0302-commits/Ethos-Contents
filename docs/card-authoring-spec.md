# 카드 작성 명세 (ChatGPT·Codex 공통, 한 장 요약)

카드뉴스를 요청받으면 긴 지침보다 이 문서를 먼저 읽는다. 목적은 **렌더에서 깨지지 않고 자연스럽게 읽히는 `card-data` JSON**과 디자인 방향을 한 번에 만드는 것이다.

**필수 읽기는 이 문서와 승인된 `content/<ID>/blog.md`뿐이다.** 아래에 나오는 다른 문서(`examples/writing/README.md`, `docs/en-legal-glossary.md`, `docs/card-patterns.md`, `docs/card-design-guide.md`, `docs/performance-learning.md`, `vendor/im-not-ai/quick-rules.md`)는 사용자가 요청하거나 QA FAIL·판단이 애매할 때만 연다. 말투가 막히면 `examples/writing/README.md` 6~8번, 영문 용어는 `docs/en-legal-glossary.md`.

초안 전에 중심 질문을 정하고 기존 `research/`와 승인 원문에서 판결·재결·공식 질의회신·통계·보도·행정자료 등 실제 근거를 먼저 살핀다. 질문에 맞는 근거를 설명의 중심에 두되 자료 종류별 의무 개수는 없으며 없는 근거를 억지로 넣지 않는다. 새 조사가 필요한 경우 공통 정본 `docs/brand-philosophy.md`와 근거 확인 기준 `docs/evidence-gate.md`를 따른다. 새 근거·장면은 원문 보강·검증·승인 후 카드에 사용한다. 적합한 사건자료가 없으면 검증된 법령·공식 안내로 설명한다. 실제 사건에 원문 밖 대화·감정·피해액·결과를 덧붙이지 않는다.

**완성 결과물은 파일로 전달한다.** ChatGPT가 작성한 `brief.md`, `card-data.ko.json`, `distribution.md`(영문 등은 별도 요청 범위)를 실제 다운로드 가능한 파일로 제공한다. 채팅에 전체 JSON이나 장문의 카드 문구를 기본으로 펼치지 않고 파일 링크와 승인·QA·렌더 상태를 짧게 안내한다. 사용자가 채팅 본문 출력이나 raw JSON을 직접 요청하면 그 요청을 따른다. 렌더 PNG나 ZIP은 실제 제작·검증된 경우에만 링크한다. 파일 전달은 Source Lock 승인·Codex 제작·발행 완료를 뜻하지 않는다.

## 역할 분담

| 누가 | 무엇을 |
|---|---|
| ChatGPT(작성자) | `brief.md`, `card-data.ko.json`(영문은 요청 시), `distribution.md`만 쓴다. 카피 초안과 **디자인 방향을 자유롭게 제안**한다(`design`·`coverStyle`·`icon`·`art`·`layout`·`highlight`). **HTML·CSS·PNG는 쓰지 않고, 윤문·재검증 패스도 돌리지 않는다** |
| Codex | ChatGPT 초안을 검수·윤문하고 영문을 현지화한 뒤 승인을 받아 HTML을 카드마다 직접 디자인하고 렌더·QA한다(`docs/card-codex-production.md`). 빠른 미리보기는 GitHub Actions `Render cards`가 JSON만으로 렌더한다 |
| 사람 | 시트(sheet-270.png)를 보고 법률 문구·여백·줄바꿈을 최종 확인하고 승인한다 |

QA 보고서에 `FAIL`이 있으면 해당 카드의 글을 줄이거나 카드를 나눠서 JSON만 고친다. 규칙을 어기며 글자만 줄이지 말고, 사실·한정어는 지킨다.

## JSON 골격 (최소 필드만 쓴다)

JSON이 짧을수록 작성이 빠르다. 렌더와 검사에 쓰이지 않는 설명 필드는 쓰지 않는다.

```json
{
  "contentId": "GAME-OVERSEAS-06", "language": "ko", "series": "게임 인허가", "issue": "No.06", "totalPages": 10,
  "editorialReview": { "pipelineVersion": "2.0", "naturalDraft": "pass", "factCheck": "pass", "marketingPass": "pass",
    "forbiddenExpressionPass": "pass", "languagePass": "pending", "semanticRecheck": "pending" },
  "approvedBy": "비교용 초안 — 사용자 승인 전. 발행 금지",
  "cards": [
    { "page": 1, "type": "cover", "bg": "navy", "headline": "…", "body": ["표지 한 줄 설명"],
      "promise": "출시 전에 답할 6가지 질문", "art": ["server", "landmark"], "takeaway": "…", "takeStyle": "bar" },
    { "page": 2, "type": "concept", "bg": "cream", "icon": "scale", "headline": "…",
      "body": [{ "key": "…", "text": "…" }, { "key": "…", "text": "…" }], "takeaway": "…" }
  ]
}
```

- **쓰지 않는 필드(선택)**: `angle`, `canvasProfile`, `visualFamily`, `marketing` 블록, 카드별 `oneMessage`·`sourceTrace`. 독자·질문·CTA 입력/결과 같은 기획 내용은 `brief.md`에 짧게 쓴다. 이전 세트에 있는 선택 필드는 그대로 둔다.
- **쓰는 것을 권장**: 카드별 `design` 한 줄(시각 중심·구도). Codex가 HTML을 디자인할 때 출발점이 된다.
- 새 `editorialReview`의 완료 상태는 `pass`·`pending`으로 쓴다. 윤문 완료 시 `languagePass: "pass"`와 실제 방법 `languageMethod: "humanize-korean"|"manual-equivalent"|"english-localization"`을 분리해 기록한다. 미완료는 `languagePass: "pending"`이며 방법은 쓰지 않는다. 기존 승인 파일의 방법명 형태 `languagePass`는 호환되므로 일괄 변환하지 않는다. 하지 않은 단계(`languagePass` 등)는 `pending`. 초안의 `pending`은 정상이며 Codex가 마친다. `scripts/validate_bilingual.py`는 Codex가 승인 요청 직전에 돌리는 관문이니 ChatGPT는 실행하지 않는다.

`approvedBy`는 사용자 승인 뒤에만 채운다. 승인 전 미리보기 렌더가 필요하면 `"비교용 초안 — 사용자 승인 전. 발행 금지"`처럼 쓴다.

## 장수 (고정)

세트는 **6~10장, 10장을 넘기지 않는다.** 스키마가 10장 초과를 오류로 막는다. 내용이 넘치면 카드를 늘리지 말고 덜어 내 `brief.md`의 OMITTED에 적거나 다음 편으로 나눈다.

영문 카드·캡션에서 행정사는 항상 **Administrative Attorney**, 사무소는 **Administrative Attorney Office**로 쓴다. 린터가 다른 번역어(administrative agent 등)를 경고한다.

## 카드 유형과 글자 한도 (공백 포함, 국문/영문)

한도는 가장 빽빽한 글자로 실제 렌더해 통과한 값이다(`scripts/spec_stress.py`). `key`는 줄바꿈 없는 한 단어가 들어가도 넘치지 않는 값이다. 한도는 기본 빌더의 시험값이다. 자유 디자인의 글꼴 크기·배치·줄바꿈까지 보장하지 않으므로 실제 렌더에서 확인한다.

공통: 헤드라인 **30/50자**(표지 40/60), 결론(`takeaway`) **56/100자**. 한 장은 한 메시지.

| type | 구성 | 한도 |
|---|---|---|
| `cover` | `body` 1줄, `promise`(끝까지 보면 얻는 것), `art`(아이콘 2~3개) | body 44/80, promise 20/36 |
| `quote` | `body` 3개: 출처 라벨 / 인용 / 한정 메모 | 48/90, 150/255, 135/225 |
| `concept` (4개) | `{key,text}` 4개 | key 14/22, text 36/69 |
| `concept` (2~3개) | `{key,text}` | key 8/16, text 60/105 |
| `comparison` (2열) | `{key,text}` 2개 | key 10/14, text 96/165 |
| `comparison` (3행) | `{key,text}` 3개 | key 6/9, text 60/105 |
| `process` | 문자열 4개(번호는 코드가 붙임) | 39/75 |
| `checklist` `layout:"questions"` | 문자열 3개 | 33/60 |
| `checklist` `layout:"stats"` | `{key,text}` 2~3개. key는 큰 숫자·키워드. key가 있으면 `layout`을 반드시 쓴다 | key 5/7, text 54/96 |
| `checklist` `layout:"bars"` | `{key,text,value,display}` 2~3개. 같은 단위의 숫자를 막대 길이로 비교. `value`는 길이 기준 숫자(화면에 안 보임), `display`는 보이는 숫자·단위(원문 표기). 항목 하나라도 `value`·`display`가 없으면 린터가 경고 | key 12/20, text 30/52, display 8/12 |
| `checklist` (기본) | 문자열 2~4개 | 70/125 |
| `flow` | `{key,text,icon}` 2~4개 + `note` | key 7/10, text 24/36, note 32/44 |
| `table` | `head` 2칸 + `{key,text}` 2~5행 | key 15/18, text 39/60, head 8/14 |
| `rest`(쉼 카드) | `headline`이 결론 한 문장, `body`는 비우거나 짧은 설명 1줄, 선택 `highlight`(강조 낱말)·`paths`(갈래 2~4개). 제목 영역 없이 문장만 크게 | headline 30/50, body 40/80 |
| `cta` (2열) | `{key,text}` 2개: 직접 준비 / 종합 검토 | key 10/14, text 105/180 |
| `cta` (6개) | 문자열 3~6개 | 38/55 |

- 선택 필드: `highlight`(강조할 구절, 제목·결론 안의 정확한 부분 문자열, 카드당 한 곳)와 카드마다 `design`(시각 중심·구도 한 줄 제안, 예: "6개월 → 3개월을 큰 숫자로"). 최종 디자인은 Codex가 한다. 영문 카드·캡션에서 행정사는 항상 Administrative Attorney(`docs/en-legal-glossary.md`).
- **숫자 비교는 막대로**: 기간·금액·건수처럼 같은 단위의 숫자 2~3개를 견주는 장은 표 대신 `layout:"bars"`를 쓴다. 단위가 다르면 쓰지 않는다(린터 `bars-units`). 원문에 없는 숫자로 막대를 만들지 않는다.
- 같은 유형 연속 3장·6장 이상에서 4개 유형은 반복감을 살피는 권고다. 정보에 맞는 구성이면 유지하고 문형·유형 비율을 맞추려고 내용을 바꾸지 않는다.
- `bg`는 `navy`/`cream` 어느 쪽이든 된다. 번갈아 쓰는 것을 기본으로 한다.
- 아이콘은 `icon`(제목 줄 배지), `art`(표지), 항목별 `icon`에 `assets/icons/lucide/` 또는 `assets/icons/tabler/`의 파일 이름만 쓴다(목록은 각 폴더의 README). 쓴 아이콘은 `assets.md`에 한 줄씩 기록한다.
- 한 카드에는 한 메시지를 둔다. 질문을 던졌다면 답을 숨기지 않는다. 근거 카드·비교 카드·쉼 카드마다 별도의 질문과 답을 강제로 넣지 않는다.

## JSON이 미리보기 디자인을 정한다 (자동 디자인)

명시한 `coverStyle`을 우선하며 회차 홀짝으로 바꾸지 않는다. 순서 없는 체크리스트에는 자동 번호를 붙이지 않는다(`layout:"numbered"` 또는 실제 `process`만 번호 사용). 막대는 0을 포함한 실제 비율로 그리며 최소 길이를 부풀리지 않는다.

새 초안에서 본문이 이미 결론을 전하면 `takeaway`는 생략할 수 있다. 법률 조건·예외가 담긴 결론이나 기존 승인된 문구는 자동 생략하지 않는다.

JSON만 올려도 CI가 `scripts/auto_design.py`로 카드마다 시각 중심이 다른 초안을 만든다(넘치면 기본 빌더로 되돌림). 아래 필드가 부품을 고르니, 디자인을 원하는 대로 이끌려면 JSON에 적는다. Codex는 이 초안을 출발점으로 다듬는다.

**자동 미리보기와 발행용 자유 디자인을 구분한다.** 자동 렌더는 카드 유형·`layout`·`art`·`icon`·항목 수 같은 구조화된 필드로 구도를 결정한다. 카드별 자연어 `design`은 Codex가 읽는 제안으로, 자동 렌더러가 자유롭게 해석해 HTML을 만들어 주지는 않는다. Codex는 `docs/card-codex-production.md`에 따라 카드마다 HTML·CSS를 직접 디자인하고 실제 이미지를 보며 여백·줄바꿈·시각 중심을 조정한다. 그래서 같은 JSON이라도 완성도에 차이가 날 수 있다. 자동 QA PASS는 읽기 쉬움이나 미감의 승인 표시가 아니다. JSON만으로 Codex와 같은 자유 디자인 품질을 보장하지 않는다.

| JSON | 자동 디자인 결과 |
|---|---|
| 표지 `art: ["gavel"]`(첫 이름이 그림이 있는 아이콘이면) | 표지에 큰 물건 그림(판사봉·저울·서류·달력·가게·트럭 등) |
| 표지 `coverStyle:"stat"` + `hero` | 표지 큰 숫자 |
| `quote` 카드 `icon:"gavel"` 등 | 출처 옆 물건 그림 + 인용 패널 |
| `concept` 항목 2~3개, 짧은 `key`(국문 6자·영문 16자 이하) | 큰 단어 좌우 대조 |
| 항목마다 `icon` | 아이콘 배지 행 |
| `checklist` + 카드 `icon:"ban"`/`"x"` | ✕ 목록(안 되는 경우) |
| `layout:"stats"` / `"bars"` / `"questions"` | 큰 숫자 행 / 막대 / 질문 패널 |
| `process` | 큰 번호 순서 |
| `cta` 항목 2개(`key` 있음) | 직접 준비 / 종합 검토 두 상자 |

## 전환 장치 (문의로 이어지게, 권고)

에토스 원칙(꾸며낸 긴장 금지, CTA는 마지막 한 번, 카드·본문에 연락처·URL·버튼 금지) 안에서 아래를 갖춘다. 린터가 배포안에서 저장 신호·다음 편·받을 자료가 빠지면 알린다.

1. **실제 기한**: 원문에 근거가 있는 기한만 쓴다(예: 사전통지서의 의견제출기한, 행정절차법 제21조 제1항 제6호·제3항). 기한이 원문에 없으면 쓰지 않는다.
2. **보낼 것 → 받을 결과**: 마지막 장 CTA에 독자가 보낼 자료와 받을 결과를 한 번에 쓴다(예: "사전통지서와 과거 처분서로 전환 가능 여부와 대응 방향"). 결과는 `brief.md`의 CTA 확인 결과 범위 안에서만. 회신 기간처럼 확인되지 않은 서비스 사실은 쓰지 않는다.
3. **받을 자료**: 원문의 확인 항목을 한 장 체크리스트로 만든 `content/<ID>/lead-magnet.md`. 캡션 안내 문구는 자료를 실제로 올린 뒤에만 쓴다.
4. **저장 신호**: 캡션에 실제 쓰임과 묶은 저장 이유 한 줄("의견서를 쓰기 전에 다시 볼 수 있게").
5. **다음 편**: 시리즈면 캡션 끝에 원문 목차 제목 그대로 "다음 편: …".
6. **측정**: 채널·위치별 추적 링크와 `performance-log.csv`. 2주 숫자로 다음 세트의 변수를 하나만 바꾼다.

## 표지 변형과 일러스트

- **대안 표지(선택)**: 표지 카드에 `altCover: {headline, promise, hookType, design}`를 더하면 Hook 유형이 다른 시험용 표지를 함께 만든다. `hookType`은 situation(구체 상황)·question(질문)·contrast(대비)·number(숫자) 중 기본 표지와 다른 것. 사실·숫자는 원문 그대로, `promise`·`takeaway`는 기본 표지와 같게 둔다. Codex가 `ko|en/alt/card_01.html`로 디자인하고, `Render cards`가 카피 잠금과 QA를 따로 본다. 쓰는 법은 `docs/performance-learning.md` "표지 시험"(같은 채널·시간대의 연속 세트에서 번갈아 쓸 때만 비교한다).

- **표지와 쉼 카드는 회차마다 번갈아 그린다(자동 디자인).** 표지에 `hero`(숫자)와 큰 그림이 있는 `art`를 **둘 다** 주면 홀수 회차는 큰 숫자 표지(A), 짝수 회차는 그림과 갈래 칸 표지(B)가 된다. 하나만 있으면 그것을 쓴다. B 표지의 칸은 `paths`(예: ["주식인수","사업양도","합병"]), 제목 강조는 `highlight`.
- **쉼 카드(`type: "rest"`)는 세트에 1장**(많아야 2장). 중반이나 CTA 바로 앞에 두고, 앞 카드들의 결론을 한 문장으로 다시 말한다. 새 사실을 넣지 않는다. 큰 따옴표형과 손 동그라미형이 회차와 순서에 따라 번갈아 나온다. `highlight`는 문장 안의 정확한 낱말이어야 한다.
- **필수: 가운뎃점 나열 금지와 결론 띠 40%.** 가운뎃점(·) 묶음은 두 낱말까지이고 셋 이상은 문장으로 푼다. 결론 띠(`takeStyle:"bar"`)는 세트의 40% 이하(9장이면 3장, 10장이면 4장까지). 린터가 `memo-style`·`take-bar-share`를 경고로 알린다.
- **결론(`takeaway`) 끝맺음을 섞는다.** 세트의 3장 이상은 "~니다"가 아닌 끝맺음(질문형 "~일까요?", 권유형 "~하세요", 짧은 명사형 "가능성보다 실익.")으로 쓴다. 사실·한정어는 그대로.
- **본문 항목은 한 문장.** 항목 하나에 두 문장을 쓰면 글자가 작아진다. 설명이 더 필요하면 카드를 나눈다.
- **표지 고르는 순서**: ① 약속·제목에 숫자가 있으면(예: "계약 전 5가지") `coverStyle:"stat"` + `hero`(린터 `cover-number`). ② 숫자가 없으면 `art` 맨 앞 아이콘이 자동 디자인 표지의 **큰 그림**이 되므로 이 글의 상황을 보여 주는 것을 앞에 둔다. 큰 그림이 있는 이름: gavel, scale, landmark, receipt, file-text, calendar-clock, truck, store, building-2, briefcase, stamp, laptop, ban, circle-dollar-sign, hourglass, clipboard-check, search, handshake(없으면 린터 `cover-object`). ③ 앞선 회차와 같은 큰 그림은 피한다(린터 `cover-art-repeat`).
- `coverLabel`(표지 칩)은 시리즈 이름과 다른 **이번 회 주제**로 쓴다. 쓰지 않거나 시리즈 이름과 같으면 v2 세트에서는 칩을 그리지 않는다(헤더에 이미 시리즈 이름이 있다).
- 표지는 `coverStyle`로 고른다. `art`(기본, 아이콘 원 2~3개), `panel`(자체 일러스트 패널, `illustration` 필요), `stat`(큰 숫자 `hero: {value, label}`, 숫자는 원문 근거 필요).
- `panel`·`stat` 표지는 글이 더 들어가지 않는다: 헤드라인 **30/52자**, `body` **28/64자**.
- `hero.value` 3자 이하, `hero.label` 10/16자 이하.
- 일러스트: `balance`, `bridge`, `calendar`, `documents`, `layers`, `route`(`assets/illustrations/`, 자체 제작). 본문이 짧은 카드에 `illustration`을 쓰면 제목 아래에 들어간다. 본문이 길거나 제목이 길면(국문 24자·영문 36자 초과) **자동으로 생략**되니 일러스트에 의존하는 메시지를 쓰지 않는다.
- 본문이 짧은 카드는 렌더러가 글자와 패널을 자동으로 키운다(`pipelineVersion: "2.0"` 세트만). 빈 공간을 글로 채우려고 문장을 늘리지 않는다.

## 정보량: 얇지 않게 채운다

레이아웃이 깨지지 않아도 카드가 얇으면 저장·공유할 이유가 사라진다. 한도는 위 표의 **상한까지 쓰는 것이 기본**이고, 짧게 쓰는 것은 의도가 있을 때만이다.

- **분량 기준(2026-10-07, 승인본 실측으로 확정)**: 세트 평균 보이는 글자(헤드라인+본문+결론, 공백 포함) **국문 130~210자, 영문 280~440자**, 목표는 **국문 150~190자, 영문 300~400자**. 승인본은 국문 133~165자, 영문 287~368자였다. 카드 한 장은 **국문 180자(강한 경고 240자), 영문 340자·60단어(강한 경고 420자·72단어)**를 넘지 않게 쓴다(QA는 공백 제외로 센다). 영문은 국문의 약 2.2배 글자가 정상이다. 평균이 상한을 넘으면 글자가 작아져 휴대폰에서 읽기 어려우니 린터가 `dense-set`으로 알린다. 린터가 평균이 하한 아래면 `thin-set`, 하한의 70% 미만인 본문 카드가 3장 이상이면 `thin-cards`로 알린다(권고).
- 본문 항목마다 **조건·기준·예시 중 하나**를 담는다. "~가 중요합니다"처럼 결론만 있는 항목은 얇은 것이다. 근거는 원문에 있는 것만 쓰고 지어내지 않는다.
- 한 장은 여전히 한 메시지다. 정보를 늘리려고 메시지를 두 개 넣지 말고, 넘치면 카드를 나눈다.
- **저장용 카드 한 장**: 세트마다 한 장은 나중에 다시 꺼내 볼 만한 `table`(기준 비교) 또는 `checklist`(준비물·확인 순서)로 만든다. 가장 정보가 밀도 있는 카드이므로 이 장은 상한 가까이 채운다.
- 쉼 카드(큰 결론 한 줄)는 세트에 한 장까지.
- **시각 요소를 빼먹지 않는다**: 표지는 `art`(아이콘 2~3개)나 `coverStyle`, 카드 3분의 1 이상에 `icon`, 세트의 가장 강한 숫자는 `stats`·`bars`·`hero`. 쓰지 않으면 린터가 `plain-set`·`plain-cover`로 알린다.

## 독자가 한눈에 이해하는 카드 구성 (Soft Guide)

기본은 독자가 자기 문제를 발견하고 법률을 이해하며 맡길 일을 판단하는 칼럼의 흐름이다. 자료 받기→작성→제출을 모든 세트의 뼈대로 강제하지 않는다. 사용자가 절차서를 요청하면 그 형식을 따르고, 필요한 절차·비용·기한은 보조 정보로 남긴다. **원문에 근거가 있는 판단의 차이**를 짧은 문장과 시각적 대조로 보여 준다.

- **표지**: '누가 어떤 상황에서 무엇을 확인해야 하는가'를 나타내는 사물·상황 또는 독자의 질문을 쓴다. 출처에 없는 피해액·제재 기간이나 실제 고객을 연상시키는 꾸며낸 후기는 쓰지 않는다.
- **중간 카드**: 같은 판단 기준 아래 서로 다른 조건이 어떻게 작용하는지 보여 줄 근거가 있으면 `comparison`·`flow`·`checklist`로 표현한다. 연속 카드가 같은 주장을 반복하면 합치거나 덜고, 원문의 조건 차이·문서 항목·같은 단위의 수치를 비교해 판단에 필요한 차이를 보여 준다. 비교를 위해 숫자를 만들지 않는다. 모든 카드에 생활 사례를 넣거나 같은 말풍선·상자·아이콘 구도를 반복하지 않는다.
- **한 장 한 메시지**: 한 화면에 '상황·법리·절차·홍보'를 모두 넣지 않는다. 상황 카드에서는 문제를 이해시키고, 후속 카드에서는 확인할 조건과 서류를 보여 준다. 질문형 카드에도 원문에 근거한 답을 함께 둔다.
- **결론과 행동**: 추상적인 '전문가 검토 필요' 대신 원문에 있는 확인 자료나 절차 한 가지를 명시한다. CTA는 정해진 마지막 역할 안에서만 쓴다.
- **가상 사례·출처 잠금**: 승인 블로그의 인물·대화·조건·법률 의미·서비스 범위를 보존해 압축한다. 새 인물·대화·장면·비교가 필요하면 원문 초안에 보강하고 사실·법률을 검증하여 승인받은 뒤 사용한다. 승인 전 파생물에 독자적으로 보태지 않는다. 실제 사건을 가상의 대표사례로 바꾸지도 않는다. 중요한 조건과 재량·예외는 카드를 단정적으로 만드는 과정에서 삭제하지 않으며, 조문 출처 등 긴 근거 표기는 기존 캡션 규칙을 따른다.

국문 카피 초안과 디자인 방향 제안은 ChatGPT, 윤문·영문 현지화·렌더·QA는 Codex, 최종 승인은 사람이 맡는 현재 역할 분담과 JSON 필드·글자 한도는 그대로 유지한다.

## 맡길 일이 보이는 자연스러운 카드 (2026-10-15 보강, Soft Guide)

`docs/brand-philosophy.md`의 문제 해결형 전문성을 이 요약으로 적용한다. 정본을 매번 추가 조회하지 않는다.

- 새 글·후속편·새 시리즈·수정본의 모든 카드 세트에 **독자의 생각과 질문, 중심 답·관점, 법률 근거와 조건 비교, 자기 적용, 실제 맡길 작업**을 자연스럽게 연결한다. 고정된 장별 순서나 장면→조문→CTA 공식이 아니다. 이야기·법률 전문성·전환성은 세트 전체에서 함께 살리며 한 장에 모두 몰아넣지 않는다. Traffic·Authority·Revenue는 주된 역할일 뿐 나머지 요소를 생략하는 구분이 아니다.
- 예시는 '신청서와 증명서의 이름이 다르다면?'처럼 조건문으로 드러낸다. 발행 카드·캡션에 '가상의 사례입니다', '실제 상담 사례가 아닙니다' 같은 독립 안내문을 붙이지 않는다. 민수·지연·준호 등 다양한 예시 이름과 인물 간 짧은 대화를 허용한다. 이름 자체보다 서로 다른 생각·오해·여건이 드러나는지가 중요하다. 이름·대화 수를 고정하거나 같은 설명에 이름만 바꾸지 않는다. 조건문 외에도 「예를 들어 민수 씨와 지연 씨가 같은 양식을 본다면」처럼 문맥에서 예시임을 드러낼 수 있다. 허구를 에토스의 실제 고객·상담·수임·후기·성과로 주장하거나 공무원·판사·기관의 말을 창작하는 것은 금지한다. 대사 속 오해는 인접한 설명에서 풀고 법률 결론은 공식 근거에 맞춘다. 조건형 장면 자체가 새 법률 결론의 근거가 되지는 않는다.
- 표지의 질문에 답하고, 승인 원문에 있는 자료와 실제 수행 작업을 연결한다. '종합 검토'라는 말만 반복하기보다 어떤 자료를 맞춰 무엇을 정리하는지 핵심 작업을 보여 준다. 기존 카드 수 안에서 설명하며 별도 홍보 카드를 의무로 추가하지 않는다.
- 말로 한 초안에서 상황과 이유를 먼저 연결한 뒤 압축한다. 한도를 맞추려고 '서류·요건·정합성 검토' 같은 명사 나열로 되돌리지 않는다. 원문에 있는 공식 용어는 뜻을 붙여 남기고 사실·의무·재량·예외의 강도를 보존한다.
- 실제 작업과 허가·처분 변경 같은 외부의 결정은 구분한다. 제공하지 않는 보고서·보완 대응·회신기한을 만들거나 유료 작성을 무료 검토 결과처럼 쓰지 않는다. 마지막 안내는 보낼 자료와 먼저 받을 안내를 독자의 말로 쓴다.
- 표지 질문, 유용한 비교, 저장할 기준은 살리고 추상적인 반복만 덜어낸다. 모든 카드에 같은 문장 틀을 적용하지 않는다. 새 예시는 위 Source Lock의 원문 보강·검증·승인을 따르고 수임 실적은 창작하지 않으며, 원문에 업무 설명이 없으면 만들어 채우지 않는다.
- 작성 시점에 확인한 공식 근거와 승인 원문을 잠그고 주체·대상·의무·재량·조건·예외·기간·숫자·출처를 보존한다. 압축할 때도 '또는', '이하', '수 있다'를 삭제하지 않는다. 넘치는 문구는 불필요한 반복을 덜거나 기존 허용 장수 안에서 나누며 필드 한도를 완화하지 않는다.
- 국문·영문·아랍어 등 요청 언어마다 질문의 방향, 법률 조건, 실제 서비스 범위와 다음 행동이 같은지 대조한다. 표현은 독자의 업무 문맥에 맞추되 새 업무·성과를 보태지 않는다. 이 원칙은 지원하지 않는 언어의 카드 스키마나 렌더 기능을 새로 허용하는 뜻이 아니다.
- 마지막 안내는 독자가 직접 준비할 일과 맡길 작성·제출 작업을 구분하고, 현재 보유한 자료로 먼저 무엇을 확인할지 설명한다. 내용은 이해했지만 직접 작성할 시간이나 여력이 없는 독자도 맡길 일을 판단하게 한다. 자료를 전부 완성해야 문의할 수 있는 것처럼 쓰지 않되 무자료 검토·미확인 보고서·처리기한·등록 성공·보완 대행을 약속하지 않는다. 무료 사전 검토와 유료 작업은 구분한다. 승인된 서비스 범위에 없는 작업은 약속하지 않고 원문 보강사항으로 남겨 확인·승인을 받는다.

공개 카드·캡션에는 독립적인 확인 기준일·검증 기준일 라벨을 넣지 않는다. 실제 확인일과 판본은 내부 검수 기록에 남기고 법령 시행일·판결일·통계기간은 보존한다. 카드에 별도 3줄 요약을 추가하지 않으며 마지막 CTA 구조를 유지한다.

`docs/blog-authoring-spec.md` 6절의 최종 3질문을 공통 편집 관점으로 참고하되 기존 채널 QA는 유지한다. 그 점검 안에서 근거가 중심 질문을 설명하는지, 카드마다 새로운 판단 정보가 있는지, 실제 맡길 일이 드러나는지를 함께 본다. 새 점수표나 검수 패스를 만들지 않는다.

장수·필드 한도·JSON 최소 골격·디자인·Source Lock과 ChatGPT/Codex의 역할은 그대로다. 이 절은 추가 윤문 패스나 점수·사례 개수 기준이 아니다.

## 카드 문구는 두 번에 나눠 쓴다

한 번에 카드 크기에 맞춰 쓰면 법률 문서 말투가 된다("개별기준 기간은 2분의 1 범위에서 줄일 수 있습니다"). 그래서 두 단계로 쓴다.

1. **말로 한 초안**: 카드마다 그 장의 메시지를 의뢰인에게 말로 설명하듯 한두 문장으로 먼저 쓴다. 글자 수는 신경 쓰지 않는다. 예: "규칙에 정해진 기간이 있는데, 사정이 인정되면 그 절반까지 줄여 줄 수 있어요."
2. **카드로 줄이기**: 그 말투를 살린 채 필드 한도에 맞게 줄인다. 사실·숫자·한정어(수 있·이하·또는)는 원문 그대로 둔다. 예: "기준 기간은 절반까지 줄어들 수 있습니다."(원문에 "2분의 1"이면 숫자 표기는 원문대로)

말로 한 초안은 `brief.md`의 카드별 한 메시지 아래에 남긴다(카드에는 넣지 않는다). 압축 뒤에도 말로 읽어서 어색하면 1단계로 돌아간다. 원문 용어(예: 별표 4, 사전통지)는 독자가 실제 서류에서 마주치므로 그대로 쓰되, 처음 나올 때 풀이를 붙인다.

## 자연스러운 문구 규칙 (린터가 보는 것)

**카드에도 자연스러운 한국어를 적용한다.** 짧은 제목·본문·결론이라고 해서 '이와 연결됩니다' 같은 빈 연결말이나 명사만 이어 붙인 메모체를 쓰지 않는다. 한 장은 한 메시지를 독자가 알아듣는 말로 전하고, 누가 무엇을 하는지 직접 쓰며 어색한 명사형은 쉬운 동사로 고친다. '서류의 정합성을 검토'보다 '신청서와 증명서의 이름을 맞춰 확인'처럼 보여준다. 카드 글자 한도 안에서도 공식 법률용어·주체·조건·예외·숫자·한정어는 유지한다. ChatGPT는 자연 초안과 글자수 압축까지, Codex는 기존 국문 윤문·의미 재검증 단계에서 이 문장을 확인한다. 새 사례·재작성 패스나 글자 한도 완화는 없다. 영문은 현지 독자에게 자연스러운 말투로 현지화한다.

1. 질문형 헤드라인 비율은 반복감을 보는 참고값이다. 실제 독자 질문은 유지하고, 확인된 답은 단정형으로 쓴다.
2. 부정 결론 비율도 권고다. 사실에 맞는 `아닙니다`를 억지로 긍정문으로 바꾸지 않는다. 근거 없는 양시론·양비론은 피한다.
3. 카드 한 장에 **조문 번호는 1개 이하**. 근거 조문은 캡션 맨 끝 `근거:` 줄로 옮긴다. 판례 번호는 `quote` 카드의 출처 라벨에만 쓴다.
4. 전문용어는 첫 등장에 한 줄 풀이(`—`, `:`, 괄호, `~이란`)를 붙인다. 용어 목록은 `content/<ID>/terms.json`.
5. **숫자+단위**는 원문과 같은 표기를 유지한다. 표지 `promise`에는 독자가 얻을 답을 한 줄로 쓴다. `내게 필요한 출시 절차를 구분합니다`처럼 숫자 없는 약속도 좋다. 숫자를 쓸 때만 원문 근거를 확인하며, 표지 형식을 위해 숫자를 만들지 않는다.
6. 반복 동사와 문장 길이부터 다듬는다. 종결어미의 비율을 맞추려고 사실·의무·재량을 바꾸거나 완결된 문장을 메모체로 만들지 않는다.
7. 영문은 국문의 직역이 아니다. 질문의 **방향**(`없어도 될까요?` ↔ `Can you launch without…?`)이 뒤집히면 안 된다.
8. 숫자와 단위 사이, `네 가지` 같은 수관형사와 단위명사 사이에는 줄바꿈이 끼지 않게 NBSP(` `)를 쓴다.
9. **세트에서 가장 강한 숫자 대비**(예: "사전통지 6개월 → 최종 3개월")는 작은 표로 두지 말고 `checklist` `layout:"stats"`(큰 숫자 행)나 표지 `coverStyle:"stat"`으로 시각 중심을 만든다. 숫자는 원문 표기 그대로.
10. **결론 띠(`takeStyle:"bar"`)는 세트의 40% 이하.** 표지·마지막 장·핵심 판단 카드에만 bar를 쓰고 나머지는 `"close"`(구분선 한 줄)로 둔다. 모든 장에 bar를 달면 세트가 양식집처럼 보인다.
11. 항목이 2~3개뿐인 카드가 연달아 나오면 하나로 합치거나, 그중 하나를 글이 적은 쉼 카드(큰 결론 한 줄)로 바꾼다. 렌더러가 본문을 남는 높이만큼 키우지만(최대 1.5배), 내용이 얇은 카드가 연속되면 세트가 헐거워 보인다.
12. **카드 문구는 메모가 아니라 말이다.** 글자 한도를 맞추려고 명사를 가운뎃점으로 이어 붙이지 않는다("과실·시정 노력·동기와 결과 등을 봅니다" → "실수였는지, 바로잡으려 했는지, 결과가 어땠는지를 봅니다"). 가운뎃점 묶음은 두 낱말까지. 한도는 권고이고, 넘치면 렌더가 알려 준다. 영문은 문장형(대문자로 시작, 완결된 문장)으로 쓰고 조문 번호(`Article 21-5`)는 라벨로 쓰지 않는다.
13. 카드마다 `design`에 시각 중심과 구도를 한 줄로 제안한다(예: "실제 순서 네 단계를 큰 숫자로", "두 기준을 좌우로 대조"). Codex가 `docs/card-design-guide.md`로 최종 디자인할 때 출발점이 된다. 문구는 바꾸지 않는다.
14. 마지막 카드는 직접 준비할 범위와 종합 검토가 필요한 경계를 보여 준 뒤, 무료 검토 안내 **한 문장**으로 끝낸다. 연락처·URL·버튼은 넣지 않는다.

## 제출물 점검 (자주 빠지는 것)

- 카드에 쓴 아이콘의 `assets.md` 기록은 Codex가 제작 단계에서 한다. ChatGPT 초안 단계의 `icon-unrecorded` 경고는 무시해도 된다.
- `distribution.md`에는 상담 접수 추적 링크(`PROJECT_INSTRUCTIONS.md` "마케팅·추적" 형식)를 넣는다. 해시태그도 같은 낱말 3개까지.
- 글에 `[미확인]` 표시를 남겼다면 발행 전에 반드시 확인해 지우거나 문장을 바꾼다. 카드·캡션에는 남기지 않는다.
- 용어 풀이(`—`, `:`, 괄호)는 같은 카드 안에 있으면 된다.

## 마지막 윤문 (Codex 단계)

ChatGPT는 위 "두 번에 나눠 쓴다"까지만 하고 `languagePass: pending`으로 넘긴다. 국문 윤문(`vendor/im-not-ai/quick-rules.md`)과 의미 재검증은 Codex가 승인 요청 전에 한다. 숫자·조문·날짜·고유명사와 "수 있", "이하", "또는" 같은 한정어는 바꾸지 않는다. PR이 올라오면 CI가 이전 버전과 비교해 사실 토큰이나 한정어가 줄면 PR 댓글로 알린다.

## 쓰지 않는 것

운영체제 이모지 글꼴에 의존하는 카드 렌더, `+`·`=`·`≠` 기호(승인 없이), 그라데이션 요청, 경험담·후기·성과 창작, 원문에 없는 숫자·조문·판례, "무조건·100%·최고" 같은 보장 표현, 카드 안 연락처.

## 제출 전 자가 점검 (린터를 실행하지 못할 때)

- [ ] 질문·부정·어미 반복이 실제로 읽기를 방해하는 곳만 고쳤다 / 카드당 조문은 1개 이하 권장
- [ ] 표지 `promise`가 구체적인 답을 예고한다(숫자는 선택이며 쓸 경우 원문 근거 필요)
- [ ] 모든 필드가 위 한도 안이다(넘으면 줄이거나 카드를 나눈다)
- [ ] 첫 등장 전문용어에 풀이가 있다
- [ ] 국·영문 카드 수·순서·유형이 같다(`sourceTrace`를 쓴 세트는 그것도)
- [ ] 세트 전체에서 독자의 질문과 오해가 법률 설명·자기 적용·맡길 업무로 연결되며 매 카드에 세 요소를 몰아넣지 않았다
- [ ] 새 예시는 원문 보강·검증·승인 후 사용했고 실제 경험 주장과 구분했다
- [ ] 확인일·판본은 내부에 기록했고 공개 독립 확인일 라벨·추가 3줄 요약은 없다
- [ ] 마지막 카드가 무료 검토 한 문장으로 끝난다

완료 보고에서는 문구 개요, JSON 초안, 렌더·자동 QA, 실제 이미지 시각 검토의 상태를 구분한다. 자동 QA 통과는 디자인 품질이나 법률 검증 완료를 뜻하지 않는다. 만들거나 열어 보지 않은 결과는 완료로 보고하지 않는다.

저장소에 올리면 `Render cards` 워크플로가 같은 항목을 코드로 다시 확인하고 렌더한다. 린터(`python scripts/copy_lint.py content/<ID>`)와 한도 검증(`python scripts/spec_stress.py`)이 기준이며, 임계값은 `copy-rules.json`과 `card-limits.json`에 있다.

문체 예시가 필요하면 `python scripts/writing_context.py --purpose card`로 카드 편집 사례만 읽는다. 문장을 베끼지 말고 명사 나열을 독자의 판단으로 바꾸는 이유, 결론 반복을 줄이는 이유를 적용한다. 법률 결론은 현재 승인 원문에서만 가져온다.

## 의미가 보이는 시각 편집 (2026-10-25 사용자 채택)

새 카드와 후속편에도 다음 원칙을 기본 적용한다. OEM 시안은 구도 참고이며 문구·법률 결론을 다른 주제에 복사하지 않는다.

- 글만 나열하기 전에 문서·공장·상자·돋보기 등 메시지에 맞는 사물과 SVG 이모티콘을 시각 중심으로 검토한다. 개수·위치 할당이나 모든 카드에 같은 그림을 강제하지 않는다.
- `design`에는 무엇을 비교하고 어디를 읽을지 적는다. 문서 대조는 실제 문서명·대조 항목·확인 행동, 흐름은 실제 전달·보관 관계를 보여 준다. 승인 원문에 없는 예시·서류·업무는 만들지 않는다.
- 긴 법률 설명은 원칙과 예외·적용 조건으로 나눈다. ‘또는’과 ‘모두’를 구분하고, 결론 카드에도 적용에 필요한 조건을 남긴다. 다음 장에만 조건을 숨겨 단정적으로 보이게 하지 않는다.
- 색이 있는 SVG 이모티콘은 기본 허용한다. 법률 요건·의무·예외를 그림이나 체크표시로 대체하거나 허가·적합성 인증처럼 연출하지 않는다. 본문 공간이 줄면 배치부터 조정하고 자동 축소로 맞추지 않는다.
- 로컬 자산·라이선스·출처는 `docs/asset-policy.md`를 따른다. 제작자는 개별 PNG와 축소 시트를 모두 확인하고 모바일 크기에서도 문구와 조건이 읽히는지 확인한다. QA 게이트와 Source Lock은 유지한다.

채택 예시: `content/COSMETICS-OEM-04-VISUAL-DRAFT/comparison/index.html`. 재사용 자산: `assets/emoji/twemoji/`. 자유 디자인 단계에서 `<img src="../../../assets/emoji/twemoji/1f4c4.svg" alt="문서" width="64" height="64">`처럼 로컬 파일을 사용한다. JSON에 이모지 문자를 본문으로 삽입해 자동 빌더가 처리할 것으로 가정하지 않는다.
