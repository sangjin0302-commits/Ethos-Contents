# 실행 지시 — 칼럼형 설명·다양한 예시 인물과 대화·요약 위치

## 1. 사용자의 최종 편집 의도

이 문서는 PR #48의 기존 지시를 최신 요청으로 구체화한 실행 계획이다. 계획을 다시 만들지 말고 이 브랜치에서 구현한다. 이미 실행 중인 작업이 있으면 그 작업에 합치며 중복 에이전트 작업을 시작하지 않는다.

사용자는 순서대로 따라 하는 신청 매뉴얼보다, 여러 사람의 상황과 질문을 읽으면서 법률을 이해하고 자기 문제에 적용하는 칼럼을 원한다. 이름만 붙인 절차 안내나 짧은 문장으로 잘라 쓴 체크리스트가 목표가 아니다. 앞으로 새 글·후속편·새 시리즈·수정본·모든 파생 매체에 다음 요소가 함께 살아야 한다.

- 자연스럽고 읽을 만한 칼럼형 스토리텔링과 쉬운 설명
- 공식 근거에 충실한 전문지식, 주체·조건·예외를 보존한 논리
- 실제 맡길 작업과 다음 행동이 보이는 마케팅·전환

기존 '초안부터 업무 흐름으로 쓴다'를 모든 글의 번호형 순서 안내로 해석하지 않도록 고친다. 사용자가 매뉴얼·절차서를 명시적으로 요청할 때는 그 형식을 우선하며, 칼럼 안에서도 필요한 절차·서류·비용·기한은 찾기 쉬운 보조 영역으로 남긴다.

## 2. 바꿀 편집 원칙

### 칼럼을 기본으로, 이야기는 설명을 이끄는 역할로

- 도입에서는 인물의 상황이나 생활·사업상의 질문을 충분히 보여주고 핵심 답·관점을 일찍 제시한다. 이야기 때문에 답을 끝까지 숨기지 않는다.
- 사례나 짧은 대화에서 드러난 오해를 풀고, 왜 판단이 달라지는지 법률 근거와 함께 설명한다. 인물의 선택과 서로 다른 조건을 비교할 수 있다. 접수 순서를 글 전체의 필수 뼈대로 삼지 않는다.
- 예시 다음 문단도 독자의 말로 잇는다. '종합 검토·정합성·적용 가능성' 같은 추상어로 즉시 돌아가거나 매 문단을 '확인해야 합니다'로 끝내지 않는다. 공식 용어는 필요한 뜻을 붙여 보존한다.
- 절마다 동일한 장면→조문→CTA 틀, 고정 인물 수·대화 수·길이·점수는 만들지 않는다. 단순한 사실 목록을 소설로 부풀리지 않는다.

### 다양한 예시 이름과 짧은 대화를 허용

- 민수·지연·준호 등 서로 다른 이름의 예시 인물을 주제와 맥락에 맞게 활용한다. 한 글에서 여러 상황을 비교하거나 같은 인물을 이어 쓸 수 있다. 모든 글의 주인공을 민수로 고정하거나 모든 절마다 새 이름을 추가하지 않는다.
- 인물의 짧은 질문·대답과 인물 간 예시 대화를 허용한다. 이름·대화의 일괄 금지 문구를 그대로 둔 채 허용 조항만 추가하지 않는다. '허구의 예시를 금지'와 '허구를 실제 고객 경험으로 주장하는 것을 금지'를 분리한다.
- '예를 들어 민수 씨와 지연 씨가 같은 양식을 보고 이야기를 나눈다면…' 또는 조건문처럼 문맥 안에서 예시임을 자연스럽게 드러낸다. 각 문장마다 '~라면'을 반복하거나 독립된 '설명을 위한 가상 상황입니다/실제 상담 사례가 아닙니다' 고지문을 강제하지 않는다. 독자가 알아서 허구라고 추측할 것이라는 전제로 실제 사건처럼 쓰지는 않는다.
- 사무소가 실제 수임·상담한 사람으로 소개하거나 '지난주 찾아온 의뢰인', '제가 해결한 고객', 가짜 후기·만족 발언·등록 성공·손실액·처리 실적을 만들지 않는다. 공무원·판사·실제 기관의 말을 창작하여 인용하지 않는다.
- 예시 인물의 대사는 법률 근거가 아니다. 대사에 법률적 오해가 등장하면 인접한 설명에서 바로 구분하며, 실제 법률 결론과 의무·재량·예외는 공식 근거에 맞춘다.
- 법률·절차·금액·기한을 새로 정하지 않는 형식 예시: '예를 들어 민수 씨와 지연 씨가 양식 한 장을 보고 이야기를 나눈다면요. 민수 씨는 “회사 이름만 바꾸면 되는 거 아냐?”라고 하고, 지연 씨는 “여기 적힌 품질관리팀은 우리 회사에 없는데?”라고 되묻습니다. 같은 문서를 보고도 한 사람은 빈칸을, 다른 사람은 실제로 할 일을 떠올립니다.' 실제 원고에서는 관련 법률 설명을 근거와 대조한다.

### 전문성과 의뢰 판단을 함께 유지

- 이야기·대화가 조문, 판결, 통계, 실제 사실확인을 대신하지 않는다. 확인된 법률적 결론은 분명히 말하고 실제 조건·예외만 한정한다. 날짜·숫자·주체·업무범위를 보존한다.
- 사무소를 이야기의 영웅으로 만들지 않는다. 독자가 왜 막히는지, 직접 무엇을 알아볼 수 있는지, 실제 제공 범위에서 어떤 서류 작성·제출 업무를 맡길 수 있는지 보여준다.
- 이해가 어려운 사람뿐 아니라 내용을 이해했지만 직접 서류를 작성할 여력이 없는 독자도 의뢰 여부를 판단할 수 있게 한다. 무료 사전 검토와 유료 작성·제출은 구분한다. 자료를 전부 완성해야 문의할 수 있는 것처럼 쓰지 않는다.
- 글자 수를 늘리거나 상담 권유를 반복하는 것으로 전환을 강화했다고 평가하지 않는다. 문의·수임 증가 효과는 실제 데이터 없이는 단정하지 않는다.

## 3. 이전 요청도 유지

- 블로그: 제목 → 독자 상황·인사 → 충분한 도입 → 시리즈 목차·공통 문장 → 칼럼 본문 → 무료 검토 1회·기존 상담 이미지 영역 → 3줄 요약 → 태그. 요약은 앞에 다시 넣지 않는다. 도입의 직접 답은 요약 없이 자연스러운 일반 문장으로 전달한다.
- 발행 본문·캡션의 독립적인 확인 기준일/검증 기준일 라벨은 제외한다. 실제 확인일과 판본은 내부 research/검수 기록에 남기고 법령 시행일·판결일·통계기간 등 의미 있는 날짜는 유지한다. 웹사이트 관리용 날짜 필드·코드·스키마는 변경하지 않는다.
- 블로그 8,000~11,000자, 무료 검토 1회와 기존 상담 이미지 4개의 순서·연결 주소는 유지한다. 원래 3줄 요약이 없는 짧은 SNS·카드에는 새 요약을 강제하지 않으며 마지막 카드 CTA 등 채널 구조를 유지한다.

## 4. 앞으로도 작동하도록 연결할 범위

최신 main의 MANIFEST.md와 AGENTS.md에서 Active 경로를 확인하고 해당 문서의 관련 부분만 읽는다. 기존 공통 문서에 정본을 두고 각 채널의 빠른 명세에는 독립적으로 적용할 수 있는 짧은 실행 요약을 넣는다. 새 지침을 중복으로 쌓지 않는다.

- 공통 문체·충돌: docs/language-quality-workflow.md, 필요한 경우 docs/brand-philosophy.md와 docs/content-architecture-system.md의 관련 절.
- 블로그·웹사이트: docs/blog-authoring-spec.md, docs/website-md-spec.md.
- 카드·SNS: docs/card-authoring-spec.md, docs/sns-authoring-spec.md.
- 진입 경로: AGENTS.md, MANIFEST.md, 필요한 경우 PROJECT_INSTRUCTIONS.md. 예시는 examples/writing/의 기존 예시집에 재사용 가능하게 정리한다. 세부 상위 문서는 충돌이 확인된 부분만 수정한다.
- 국문·영문·아랍어, 블로그·웹사이트·카드뉴스·카카오·LinkedIn·Instagram·Threads·X·숏폼에 적용한다. 카드에서는 세트 전체의 흐름과 필요한 말풍선·비교 카피로 구현하며 매 카드에 이야기·법률·홍보를 모두 넣지 않는다. 짧은 SNS는 한 상황·핵심 답·조건·다음 행동을 매체에 맞게 남긴다.
- 파생 콘텐츠는 승인 원문에 있는 인물·조건·법률 의미·서비스 범위를 보존한다. 승인 원문에 없는 새 인물과 대화가 필요하면 초안 보강과 의미 검증·승인을 거쳐 Source Lock에 포함한 뒤 파생한다. 단순히 '같은 스토리텔링 원칙'이라는 이유로 새 사건이나 결과를 만들지 않는다. 번역에서도 허구의 실제 고객·후기를 추가하지 않는다.
- '가상 대화 금지', '꾸며낸 이름 금지', '업무 순서가 기본', '첫머리 3줄 요약', '공개 확인일 필수'의 관련 문구를 찾아 충돌을 해소한다. 사실·법률 보호는 낮추지 않는다.

## 5. 빠른 실행과 보호범위

계획은 확정되어 있다. 지원되는 빠른 하위 에이전트 A는 블로그·웹사이트 명세, B는 카드·SNS 명세를 서로 다른 파일에서 편집한다. 조정자는 공통 문체·라우터·예시·변경기록을 소유해 충돌 없이 통합한다. 검증 담당 C는 통합 후 읽기 중심으로 보호범위와 샘플을 확인한다. 지원하지 않는 모델 배정·하위 에이전트·병렬 실행을 했다고 보고하지 않는다.

한 번의 통합 점검에서 필요한 부분만 고친다. 기존 im-not-ai 규칙집과 예시집은 문체 교정에 필요한 곳에만 사용하고, 새로운 도구 탐색·외부 유료 API·전체 원고 재작성·이미지 렌더링을 기본 실행에 넣지 않는다.

기존 승인/예약 콘텐츠, 렌더러·CSS·스키마·카드 한도, 상품·가격·접수 URL은 변경하지 않는다. 작업지시서 외 현재 ③편 원고는 이 PR에 첨부되어 있지 않다. 없는 원고를 읽거나 검증했다고 말하지 않는다. 새 검증 샘플은 tests/examples 등 실제 저장소 관례에 맞는 예시 경로에만 두고 발행 원문으로 취급하지 않는다. 이 브랜치에서만 작업하며 main 직접 쓰기·자동 병합·발행은 하지 않는다.

## 6. 완료 기준

- 각 빠른 명세만 읽어도 칼럼 기본값, 다양한 예시 인물·대화 허용, 실제 수임/후기 창작 금지를 함께 이해할 수 있다.
- 같은 근거에 기반한 짧은 블로그 도입과 중간 설명, 카드 카피 세트, 짧은 SNS 문구로 자연스러움·법률 의미·의뢰 판단을 직접 검토한다. 대화가 도입에만 있고 이후 내용이 추상적인 지시문으로 돌아가지 않는지 확인한다. 매체별 적용과 영문·아랍어의 보호 기준은 대응표로 남기되 전체 분량의 다국어 콘텐츠 제작은 하지 않는다.
- 허용 예시(민수·지연의 명시된 예시 대화)와 금지 예시(에토스가 맡아 성공시킨 실제 고객처럼 꾸미기)를 대조하여 지침의 모호함을 줄인다. 예시 숫자·법률 조건은 기존 확인 근거에서만 가져온다.
- python scripts/validate_guidelines.py 및 변경 범위 관련 실제 검사를 수행한다. 사용자 요청으로 바꾼 고정 명세에 한해 기존 절차로 freeze 지문을 갱신하고 CHANGELOG.md에 사유를 적는다. 관계없는 불일치는 숨기거나 일괄 승인하지 않는다. 스크립트가 다르면 현재 저장소의 명령을 확인한다.
- 샘플의 편집 적합성과 CI 결과를 구분한다. CI 성공만으로 자연스러움이나 실제 전환을 검증했다고 하지 않는다.
- 종료 보고: 변경 파일·핵심 전후 예시·실제 검사 결과·사용한 에이전트·구현 커밋·남은 제한. 작업지시서 기록, 구현, 검증, main 병합을 구분하고 승인 전에는 이 PR을 병합하지 않는다.
